= Reloading Configuration

Tilegroxy supports automatic hot-loading of configuration without a restart or downtime when running as a server. Reloading must be explicitly enabled via the CLI parameter `--hot-reload`.

Reloading occurs automatically within a few seconds of the configuration changing on the filesystem. When reloading the configuration, the new configuration is stored side-by-side with the previous configuration and swapped atomically. The exact timing of that change cannot be controlled but should occur within several seconds of configuration being updated depending on the size of your configuration.  Requests that are already in-flight while this change occurs will continue operating against the old configuration while requests coming in after the swap completes will use the new configuration.

== Warnings

Configuration changes that affect the core functionality of the service (for example changing the port of the HTTP server) still require a restart of the executable.

When reloading occurs, new connections will be established for configured xref:configuration/datastores/index.adoc[datastores] and caches. The previous connections are closed once in-flight requests using them have had time to complete, therefore the number of connections returns to its steady state instead of growing with each reload. Expect a temporary period after each reload where both the old and new connections are open.

Buffered xref:configuration/analytics/index.adoc[analytics] events are flushed before the previous configuration is released so a reload doesn't lose the current batch.

Tilegroxy uses link:https://github.com/fsnotify/fsnotify[fsnotify] to detect when configuration has changed. It is possible for the file change event to reach tilegroxy before the file has finished being written. Tilegroxy waits 1 second before applying changes to avoid this but if you are using a filesystem with especially slow writes it is possible tilegroxy will attempt to read the configuration too early. This will usually result in an invalid configuration which will be ignored but could result in operating against incorrect configuration.  It is therefore recommended to avoid using hot reload if you're at risk of slow writes, especially if using YAML configurations.

Automatic configuration reloading will not work with remote providers (such as etcd) or certain file systems that do not support file notifications (such as NFS, SMB, or FUSE).

The following sections of the configuration can be reloaded:

* xref:configuration/datastores/index.adoc[datastores]
* xref:configuration/analytics/index.adoc[analytics]
* xref:configuration/layer.adoc[layers]

The following sections can be partially reloaded:

* xref:configuration/error.adoc[error]
** Overall error handling mode will not be changed but most error messages can be hot reloaded

Changes to unsupported sections will be ignored.


== Shutdown

For cases where you need to terminate the tilegroxy instance (when changing a non-reloadable section of config, or cycling pods), tilegroxy supports graceful shutdown to ensure requests aren't lost

=== Shutdown behaviour

When tilegroxy receives SIGINT or SIGTERM it shuts down in a fixed order rather than exiting immediately.  This gives batched analytics a chance to flush and connection pools a chance to close.  

The phases run in this order:

. Health readiness starts returning 503 while liveness keeps returning 204
. Wait for DrainDelay
. The HTTP server finishes the requests already in flight
. The health server and its background checks stop
. Entities close, which flushes analytics and releases caches, datastores and providers
. OpenTelemetry shuts down
. Log file handles close

Every phase draws from a single deadline of `ShutdownTimeout` seconds.  If the deadline passes or a second signal is sent, the remaining phases are skipped and an error is logged. 

When `ShutdownTimeout` isn't specified it defaults to `Server.Timeout` plus `DrainDelay`, which covers the two phases that consume it: the wait before draining and one full-length request finishing during the drain.  A value at or below DrainDelay is rejected as it leaves no time to drain.

A value below `Server.Timeout` is allowed but means a slow request can outlive the budget.

=== Coordinating with your orchestrator

Your orchestrator's grace period must be longer than the shutdown sequence it's waiting on, otherwise the process is killed partway through and any analytics being flushed are lost.  Three values need to stay in order:

[source]
----
preStop sleep (or DrainDelay)  <  ShutdownTimeout  <  termination grace period
----

Be careful to preserve this order when adjusting these values.  Raising `ShutdownTimeout` without also raising the grace period means the process is killed before it finishes.

In Docker Compose the grace period is `stop_grace_period` which defaults to 10 seconds and therefore needs raising for the default budget.  In Kubernetes it's `terminationGracePeriodSeconds`.  The Helm chart included with tilegroxy sets both that and a preStop hook for you.

A preStop hook runs to completion before the signal is sent, so its sleep and DrainDelay are additive.  Use one or the other, not both.  The Helm chart handles this by setting DrainDelay to 0 whenever its preStop hook is enabled.
