= Rate Limiting
:description: Rate limiting caps how many tiles can be requested in a period, anything from a burst over a few seconds to a quota over a month. Limits can apply per user, per tenant, per IP address, per layer, or any combination.

== Overview

This is useful for keeping one user from starving everyone else, keeping the total traffic to an expensive layer within what you're willing to serve, and enforcing usage quotas on a plan.  Rate limiting is disabled by default.

Limits are checked once the request is authenticated, its layer is found, and it passes authorization and zoom checks, but before the cache is consulted.  This means:

* Cache hits *are* counted
* Only the requested layer is checked.  A layer rendered indirectly through the xref:configuration/provider/ref.adoc[ref] provider isn't checked or counted separately
* Requests generated by the xref:commands/seed.adoc[seed] command, xref:commands/test.adoc[test] command, or xref:configuration/health.adoc[health checks] are never limited
* TileJSON documents and the preview page itself are never limited.  

IMPORTANT: This is not DDoS protection.  Every rejected request still reaches tilegroxy and costs a lookup against the store.  Use a CDN or WAF for that.

== Policies

Rate limiting is configured in a top-level `ratelimit` block.  Its `name` picks the xref:configuration/ratelimit/index.adoc#choosing-a-store[store] that holds the counters, and the redis and postgresql stores also need a `datastore`.  Its `policies` parameter is a list of named sets of limits.

Each policy has an `id` and a list of `rules`, described below.  Every layer is limited by exactly one policy, which it picks with its own `ratelimit` parameter.  Layers that don't pick one use the policy named by the top-level `defaultratelimit`, or the first policy if that isn't set.  Setting `skipratelimit` to true on a xref:configuration/layer.adoc[layer] exempts it entirely.

A policy can also `extend` other policies by listing their IDs, which enforces their rules as well as its own.  The rules aren't copied: a layer using the extending policy shares counters with every layer using the policy it extends.

The following gives every user a burst of 50 tiles per second on every layer, and limits each tenant to 100,000 satellite tiles a month:

[tabs]
====
YAML::
+
[,yaml]
----
ratelimit:
  name: redis
  datastore: redis-0
  policies:
    - id: standard
      rules:
        - limit: 50
          period: 1
    - id: premium
      extend:
        - standard
      rules:
        - segment:
            - tenant
          limit: 100000
          calendar: month
defaultratelimit: standard
layers:
  - id: basemap
    provider: ...
  - id: satellite
    ratelimit: premium
    provider: ...
  - id: internal_debug
    skipratelimit: true
    provider: ...
----

A policy may have no rules.  Make an empty policy the default if only a few layers should be limited.

Policies that extend each other in a loop are rejected at startup.  A policy reached through more than one `extend` is only checked once.

WARNING: If a premium layer has its own policy, any layer that reaches it through xref:configuration/provider/ref.adoc[ref] or xref:configuration/provider/blend.adoc[blend] needs that policy too, otherwise it's a way around the quota.

== Rules

Each rule allows `limit` requests per period.  A request is rejected if any rule of its layer's policy, including the policies it extends, is exceeded.  Rejected requests aren't counted against any rule, so a client that keeps retrying doesn't use up its other limits.

Each counter is updated atomically, but checking a request's rules and counting it are separate steps.  Under heavy concurrency a few more requests than configured can get through.

=== Periods

A rule's period is set with exactly one of `period`, for a rolling window, or `calendar`, for a window that follows the calendar.

`period` is the length of the window, in seconds.  Counts are kept in fixed buckets of that length, and a request is checked against the current bucket plus the previous bucket weighted by how much of it is still within the window.  For example, 15 seconds into a 60 second bucket, the estimate is the current count plus 45/60 of the previous one.  This stops a client doubling its allowance across a bucket boundary.

`calendar` takes one of `hour`, `day`, `week`, `month`, or `year`, and the count resets at the start of each one in UTC.  Weeks start on Monday.  Use this for quotas that line up with a billing cycle.  Other time zones and cycles anchored to a signup date aren't supported.

=== Segments

A rule's `segment` parameter decides what gets its own counter.  It's a list of the values below, combined, so `[tenant, layer]` gives every tenant a separate allowance for each layer.  Without `segment`, each user gets their own counter.

.Values for `segment`
[cols="1m,3"]
|===
| Value | Description

| user
| The user ID established during xref:configuration/authentication/index.adoc[authentication]. If user IDs are only unique within a tenant, use `[tenant, user]`

| tenant
| The tenant ID established during authentication. See xref:howto/multi-tenant.adoc[Serve Multiple Tenants]

| ip
| The client IP address. IPv6 addresses sharing their first 64 bits count as one client, which `ipv6Prefix` can change. Behind a load balancer this requires xref:configuration/server.adoc[`server.trustedProxies`]

| layer
| The ID of the requested layer, not the name from the URL. Every name matching a pattern layer shares one counter
|===

Without authentication, use `segment: [ip]`.

An empty list gives the rule one counter for every request to every layer using the policy.  For example, a rule with `segment: []` and a `limit` of 200 caps those layers at 200 requests per period in total.  Pair it with a per-IP rule so one client can't use it all.

Requests can arrive without a user ID or tenant ID, either because they're anonymous or because the token didn't carry one.  By default, the missing value is replaced by the client IP, so anonymous requests are counted per IP instead of all together.  Only the missing value is replaced, so `[tenant, user]` with no tenant counts by IP and user.  A rule can instead reject these requests by setting its `missing` parameter to `deny`, which suits deployments where every request should be authenticated.

NAT puts many users behind one address, so be generous with limits that count by IP.

=== Overrides

A rule's `overrides` parameter gives some requests a different limit under the same rule, such as a higher quota on a paid plan or an exemption for an internal service.  Each override has its own `limit` and matches by plan, user ID, tenant ID, IP range, or `anonymous`.  An override with several conditions matches if any one of them does.  The full list is in the xref:configuration/ratelimit/index.adoc#overrides[reference].

Overrides are checked in order and the first match wins.  Requests matching none get the rule's own `limit`.  Overrides change the limit, not what's counted, so a tenant given a higher limit still has one counter.

Prefer matching plans over listing tenants or users.  xref:configuration/authentication/index.adoc[Authentication] can take each request's plan from a token claim, a database column, or an API response, so a customer changing plan needs no configuration change.  On a rule segmented by tenant, issue the same plan to every user of a tenant; otherwise each request gets the limit of its own user's plan.

[tabs]
====

+

ratelimit:
  name: redis
  datastore: redis-0
  policies:
    - id: default
      rules:
        - segment:
            - ip
          limit: 100
          period: 1
          overrides:
            - ips:
                - 10.0.0.0/8
              limit: -1
        - segment:
            - tenant
          limit: 100000
          calendar: month
          overrides:
            - plans:
                - enterprise
              limit: 5000000
            - tenants:
                - delinquent-co
              limit: 0
            - anonymous: true
              limit: 1000

== Responses

A rejected request returns `429 Too Many Requests` with a `Retry-After` header giving the number of seconds until the exceeded rule allows another request.  For a `calendar` rule that's the start of the next period, which can be weeks away.  `Retry-After` is left out when waiting won't help, which is when the limit is 0 or the request was rejected by `missing: deny`.  It's also left out when `headers` is `none`.  The body follows the xref:configuration/error.adoc[error] mode, using the `RateLimited` image and message.

CAUTION: The `AlwaysOk` error option replaces the 429 with a 200, which most clients won't recognize as a rejection.

=== Headers

By default, every response to a request that reached the check carries headers describing the rules that applied to it.  The `headers` parameter of the `ratelimit` block controls this and can be one of:

`standard`::
The `RateLimit-Policy` and `RateLimit` headers from version 11 of the IETF https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/[RateLimit header fields] draft.  This is the default.

`min`::
No headers apart from `Retry-After` on a rejection.  Use this if you'd rather not tell users what their limits are.

`none`::
No headers at all, not even `Retry-After`.

Rules have no names of their own, so each is listed as its policy ID, segment, and period joined by dots, such as `standard.user.1s` or `premium.tenant.month`.  Multiple segments are joined with `+` and an empty segment is `all`.  The same names are used in audit events and the xref:commands/ratelimit.adoc[ratelimit command].

In `RateLimit-Policy`, `q` is the limit and `w` is the period in seconds, which for a `calendar` rule is the length of the current period.  In `RateLimit`, `r` is how many requests remain, after counting the current one, and `t` is how many seconds until the current period or bucket ends.  For a rolling period, `r` keeps rising for a while after `t`, as the previous bucket's weight falls away.

On `satellite` from the first example, a user whose tenant has made 11,201 requests this month sees:

[,http]
----
RateLimit-Policy: "standard.user.1s";q=50;w=1, "premium.tenant.month";q=100000;w=2678400
RateLimit: "standard.user.1s";r=49;t=1, "premium.tenant.month";r=88799;t=1209600
----

A rule with an unlimited override is left out of the headers for that request.

A shared cache in front of tilegroxy stores these headers with the tile and replays them to everyone.  Behind a CDN, use `headers: min` for public tiles or strip the headers at the CDN.

If you set xref:configuration/cors.adoc[CORS] `exposedHeaders` yourself, add `RateLimit`, `RateLimit-Policy`, and `Retry-After` so browser scripts can read them.

== Auditing

The following let you see who is being limited and how much of a quota has been used:

Audit log::
A `rate_limited` event naming the policy and rule is written to the xref:configuration/log.adoc#audit-logs[audit log].  Each instance writes at most one per counter per period, or per minute if the period is shorter, so a client hammering away doesn't flood the log.
Metrics::
When xref:telemetry.adoc[telemetry] is enabled, rejections are counted per policy and in total, alongside failures of the store.
Traces::
The check appears as a `ratelimit` span under the request.
Command::
xref:commands/ratelimit.adoc[`tilegroxy ratelimit`] shows how much of each rule a user, tenant, or IP address has used, and can reset it.  Resets are audited too.

Counters expire along with their period and can't be listed, so use xref:analytics.adoc[analytics] to find your heaviest users and for billing.

TIP: Alert on `tilegroxy.ratelimit.error`.  By default a store outage means nothing is being limited, while tiles keep being served normally.

== Deployment

=== High availability

Use the xref:configuration/ratelimit/redis.adoc[redis] or xref:configuration/ratelimit/postgresql.adoc[postgresql] store with more than one instance.  Otherwise each instance gives out the full limit.

Every tile request, including cache hits, costs a round trip to the store, so keep it close to tilegroxy.  When the store fails or exceeds `timeout`, `onError` decides whether the request is served or rejected.  See the xref:configuration/ratelimit/index.adoc#configuration[reference].

With several regions, either give each region its own store and divide limits by the number of regions, or share one store and accept the latency.

Behind a CDN, load balancer, or reverse proxy, list every proxy in xref:configuration/server.adoc[`server.trustedProxies`].  Otherwise the client IP is the proxy's and every anonymous user shares one counter.

=== Reloading

Rate limiting can be changed with a xref:reloading.adoc[reload].  Each rule's counters belong to the policy that defines it, so they're kept as long as that policy's `id` and the rule's `segment` and period stay the same.  Changing a `limit`, an override, or which policy a layer uses takes effect immediately without losing counts.  Changing a policy `id`, a rule's `segment` or period, moving a rule to another policy, or changing the store's own settings starts the affected counters over from zero.

During a rolling deployment that changes them, old and new instances count separately until the rollout finishes, so clients briefly get both allowances.

== Security

A limit is only as good as the identity it counts by.  Without authentication every request is anonymous, so rules segmented by `user` or `tenant` fall back to IP address.  Tilegroxy logs a warning at startup when that happens.

User IDs, tenant IDs, and IP addresses are hashed before being used as store keys, so a hostile value can't affect the key structure.  The hash isn't meant to hide them.  See xref:security.adoc[Security] for more.
