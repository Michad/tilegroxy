= Compatibility
:description: What tilegroxy's semantic versioning promise covers, how features are retired, and what is excluded.
:page-related: upgrading.adoc, extensibility.adoc, get-it.adoc

== What's Covered

Starting with version 1.0, tilegroxy follows semantic versioning.  An upgrade within the same major version (for example 1.2 to 1.5) should never require you to change your configuration, scripts, or code.

IMPORTANT: Releases before 1.0 made no such promise and frequently included breaking changes.  Read the release notes carefully when upgrading from a 0.x version.

The compatibility promise applies to four surfaces:

Configuration::
Every documented key in the xref:configuration::index.adoc[configuration], including entity names such as `memcached` and the matching environment variables
CLI::
The xref:commands::serve.adoc[commands] and their documented flags
Custom scripts::
The function signatures that xref:extensibility.adoc[custom] providers, authentication, and analytics are compiled against
Core Server Behaviour::
The way the existing production routes behave for any reasonable client (small details like header order excluded)

Minor releases may add to any of these.  A new optional configuration key, a new CLI flag, or a new field on a struct returned by a custom script are all compatible changes.  Removing or renaming any of these, or changing what an existing option does, only happens in a major release.

== Deprecation

When a feature needs to be replaced, it's deprecated first rather than removed whenever possible.  A deprecated feature:

* Keeps working exactly as it did for the remainder of the major version
* Logs a message at `warn` level on startup and on every reload for as long as it's used, naming the option and its replacement
* Is removed from the rest of the documentation to discourage its use, and listed under <<currently-deprecated,Currently Deprecated>> alongside its replacement
* Is listed under a "Deprecations" heading in the release notes of the version that deprecated it

The warning is logged at `warn` level so it shows up under the logging levels recommended in xref:howto/productionizing.adoc[Run in Production] and includes the targeted removal version.

TIP: Check your logs for deprecation warnings after every upgrade, rather than waiting for the next major release.

Setting both a deprecated option and its replacement is an error so you never have to guess which one takes effect.

=== Security Exception

If a vulnerability can only be fixed by changing or removing a feature, it may be changed in a minor or patch release.  The release notes call out the change under "Breaking Changes" with an explanation.

== What's Not Covered

The following are not guaranteed:

Library API::
The exported types and functions under `pkg/` when xref:extensibility.adoc#using-tilegroxy-as-a-library[using tilegroxy as a library]. We will try to call these changes out as Breaking Changes, but some small changes may occur in minor versions.
Cache contents::
The format of tiles written to a cache has its own versioning system and new versions may be introduced at any point. Tilegroxy maintains backwards compatibility between these versions
Seed progress files::
A progress file written by `seed` might not be resumable after an upgrade
Log messages::
The wording, fields, and quantity of log messages, as described in xref:configuration::log.adoc[Log]
Undocumented behavior::
Any configuration key, flag, or behavior not described in this documentation, even if it happens to work
The Helm chart::
Values in the chart follow the chart's own version rather than tilegroxy's
Everything under `internal/`::
Including when used through a fork
Unreleased builds::
Such as the `edge` container image tag
