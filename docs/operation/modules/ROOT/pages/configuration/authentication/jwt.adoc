= JWT

Requires incoming requests include a https://jwt.io/[JSON Web Token (JWT)]. The signature of the token is verified and grants are validated.

The verification key can either be a single key stored in configuration or supplied via environment variable, or a set of keys fetched from a remote https://datatracker.ietf.org/doc/html/rfc7517[JWKS] endpoint. See <<JWKS>>.

The following claims are supported/enforced:

[cols="1,4"]
|===
| Claim | Implementation

| exp
| Ensure the JWT hasn't expired and it's no further than a certain amount of time from now

| aud
| Validate it matches a specific value

| sub
| Validate it matches a specific value

| iss
| Validate it matches a specific value

| scope
| Validate it contains a specific scope OR ensure a given prefix plus the layer in the current request is contained in scope

| geohash
| Validate the current tile being requested is partially contained in https://en.wikipedia.org/wiki/Geohash[the geohash]. See the xref:configuration/provider/crop.adoc[crop provider] to limit raster imagery layers to precise areas
|===

Name should be "jwt"

Configuration options:

[cols="1,3,1,1,1"]
|===
| Parameter | Description | Type | Required | Default

| Key
| The key for verifying the signature. The public key if using asymmetric signing. If the value starts with "env." the remainder is interpreted as the name of the Environment Variable to use to retrieve the verification key. Required unless JWKS is supplied
| string
| No
| None

| Algorithms
| Algorithms to allow for JWT signatures. One or more of: "HS256", "HS384", "HS512", "RS256", "RS384", "RS512", "ES256", "ES384", "ES512", "PS256", "PS384", "PS512", "EdDSA". When Key is used instead of JWKS, all listed algorithms must belong to the same key family since only one key is supplied - RS and PS count as the same family
| string[]
| Yes
| None

| JWKS
| Fetch verification keys from a remote JWKS endpoint instead of Key. See <<JWKS>>
| JWKS
| No
| None

| HeaderName
| The header to extract the JWT from. If this is "Authorization" it removes "Bearer " from the start. Make sure this is in "canonical case" e.g. X-Header - auth will always fail otherwise
| string
| No
| Authorization

| MaxExpiration
| How many seconds from now can the expiration be. JWTs more than X seconds from now will result in a 401
| uint32
| No
| 1 day

| ExpectedAudience
| Require the "aud" grant to be this string
| string
| No
| None

| ExpectedSubject
| Require the "sub" grant to be this string
| string
| No
| None

| ExpectedIssuer
| Require the "iss" grant to be this string
| string
| No
| None

| ExpectedScope
| Require the "scope" grant to contain this string
| string
| No
| None

| LayerScope
| If true the "scope" grant is used to whitelist access to layers
| bool
| No
| false

| ScopePrefix
| If true this prefix indicates scopes to use. For example a prefix of "tile/" will mean a scope of "tile/test" grants access to "test". Doesn't impact ExpectedScope
| string
| No
| Empty string

| UserId
| Use the specified grant as the user identifier. This is just used for logging by default but it's made available to custom providers
| string
| No
| sub
|===

Example:

----
authentication:
  name: jwt
  key: env.JWT_KEY
  algorithms:
    - HS256
----

== JWKS

Instead of a single static Key, verification keys can be fetched from a remote https://datatracker.ietf.org/doc/html/rfc7517[JWKS] endpoint, as commonly published by an OIDC issuer. When JWKS is configured, Key must not be set.

If a token references a key ID that isn't in the currently cached keyset, the keyset is refreshed, rate limited by `RefreshMinInterval`. This lets an issuer rotate its keys without any operator action. If the issuer becomes unreachable, the last successfully fetched keyset keeps serving, so existing keys keep verifying; only tokens signed with a genuinely new key ID fail while the endpoint is down.

Configuration options:

[cols="1,3,1,1,1"]
|===
| Parameter | Description | Type | Required | Default

| URL
| The HTTPS URL of the JWKS endpoint. Plain http is rejected
| string
| Yes
| None

| RefreshInterval
| How many seconds between unconditional refreshes of the keyset
| uint
| No
| 900

| RefreshMinInterval
| The minimum seconds between refreshes triggered by an unknown key ID
| uint
| No
| 60

| RequestTimeout
| How many seconds before a fetch of the keyset is cancelled
| uint
| No
| 10

| AllowStartupFailure
| If false, a failed fetch of the keyset at startup prevents the server from starting. If true, it logs a warning instead and the server starts anyway
| bool
| No
| false
|===


Example:

----
authentication:
  name: jwt
  algorithms:
    - RS256
  jwks:
    url: https://issuer.example.com/.well-known/jwks.json
  expectedIssuer: https://issuer.example.com/
  expectedAudience: tilegroxy
----
