= Analytics as a Separate Entity from Telemetry
:date: 2026-08-08
:status: accepted

== Context and Problem Statement

Tilegroxy can report *that* tiles were served through OpenTelemetry counters and Apache-style access logs but it cannot answer which layers are actually being used and by whom. Groups proxying a metered vendor API need to attribute consumption and groups serving multiple tenants need per-tenant usage. Neither is answerable from an aggregate counter and reconstructing it from access logs means reparsing text that lacks the authenticated user entirely, since the access log handler sits outside the context that carries it.

Should this be solved by extending the existing telemetry support or by adding a distinct mechanism?

== Decision Drivers

* Per-event granularity with attribution to a layer and a user, which counters cannot express
* The destination schema belongs to the operator; usage data is usually joined against their own business data
* Tile serving must never be delayed or failed by a usage-recording destination
* Consistency with tilegroxy's existing configuration-driven, pluggable entity model
* The operator/user trust boundary: destinations are operator-configured and therefore trusted but the data flowing into them is user-derived

== Considered Options

* Extend OpenTelemetry metrics with higher-cardinality attributes
* Emit structured events into the existing main log and let operators ship them
* A new pluggable "analytics" entity with its own modules

== Decision Outcome

Chosen option: "A new pluggable analytics entity", because the other two conflate two genuinely different jobs. It follows the pattern operators already know from providers, caches, authentication and datastores of picking a module by `name` and configuring it declaratively. It also reuses the datastores system so a ClickHouse or PostgreSQL connection pool is declared once and shared.

Events are delivered on a best-effort basis. They are buffered in memory and written in batches; when the buffer fills, events are dropped by default and a periodic warning is logged. The alternative of blocking the request until there is room would turn an analytics outage into a tile-serving outage. For the use cases analytics targets, an approximate picture of usage during an incident is worth more than exact numbers at the cost of degraded map serving. Operators who disagree can set `batch.onFull` to `block` and those who need a complete record already have access logs. Buffers are flushed on shutdown and on hot reload so only abrupt termination loses events, and drops are counted in `tilegroxy.analytics.dropped` so the loss is visible.

The SQL modules never issue DDL, the documentation gives recommended `CREATE TABLE` statements instead. This keeps the credentials tilegroxy runs with free of schema privileges and leaves partitioning, ordering and retention with the operator, all of which depend on volume and local policy. The cost is more setup friction than an auto-creating table would have. Because operators name their own tables and columns, those identifiers are interpolated into SQL rather than bound. Configuration is trusted under tilegroxy's xref:operation:ROOT:security.adoc[security model] but the identifiers are still validated against a plain-identifier pattern and every event *value* is a bound parameter.

Events are recorded at the HTTP layer, at the tail of the tile handler after the response is written, and only for successful requests. Hooking lower in `LayerGroup.RenderTile` would have avoided resolving the layer a second time but would also fire for the `seed` and `test` commands, health checks, and layers rendered indirectly through the `ref` provider, none of which represent a user consuming a tile. It would also lose access to the HTTP request context that supplies the user ID and headers. Emitting after the response is written keeps recording off the latency path.

== Pros and Cons of the Options

=== Extend OpenTelemetry metrics with higher-cardinality attributes

Add attributes such as the user ID and tile coordinates to the existing counters.

* Pro: No new configuration surface, operators already have a metrics pipeline
* Con: Metrics are aggregates by design; these attributes produce unbounded cardinality that will degrade or be rejected by any real metrics backend
* Con: Traces carry per-request detail but are sampled, and sampled usage data isn't usable for attribution or billing

=== Emit structured events into the existing main log

Write each event to the main log as JSON and let operators ship it wherever they want.

* Pro: Trivial to implement, no new dependencies
* Pro: Operators with an existing log pipeline can route it without new tilegroxy configuration
* Con: Gives up typed destinations and pushes parsing, batching, schema and retention onto the operator, contradicting the project's configuration-driven philosophy
* Con: Mixes operational logs with business data, which usually have different retention and access requirements

=== A new pluggable analytics entity

Add analytics as a fifth pluggable entity alongside providers, caches, authentication and datastores.

* Pro: Usage data lands in a queryable destination the operator controls with a schema they own
* Pro: The module boundary makes destinations independently testable and lets third parties add their own through the `custom` module
* Pro: It forced a general `Closer` contract, which also fixed a standing bug where hot reload leaked every connection pool
* Con: A fifth pluggable subsystem to document and maintain, with some structural duplication of the existing registration boilerplate
* Con: Operators now have three overlapping observability surfaces in metrics, access logs and analytics, and must understand which answers which question
