= Hot Load

Tilegroxy is designed to minimize downtime by supporting hot-reloading of configuration. 

== Mechanism

Entities (layers, caches, analytics, datastores) are grouped into a generation.  A hot reload constructs a second generation and swaps it in, therefore the old generation must be released without disturbing the requests still using it.

Each generation carries a reference count.  A tile request takes a hold on the generation it reads and drops it when the request finishes so a retired generation closes as soon as its last request returns.  This replaced a fixed sleep that waited out the request timeout before releasing; with a 60 second timeout, several config saves in a row would pin several full generations at once, each holding its own connection pools.

The reference is taken inside the same lock that reads the generation pointer to avoid a race with the swap.  A request either increments before the swap occurs and is visible to the outgoing generation, or it blocks and reads the new pointer instead.  Taking the reference after releasing the lock would leave a window where a reload sees a count of zero and closes a generation that a request is about to use.

A registry holds every live generation so shutdown can release all of them rather than only the one currently serving.  Without it, a reload landing shortly before shutdown would leave the previous generation's analytics batcher draining with nothing waiting on it.

Every HTTP handler reads the generation through one shared holder, so a reload swaps the pointer once and retires the outgoing generation once.  When each handler kept its own pointer, the first swap started the close timer while the other handlers were still serving from the old generation.

The health subsystem is rebuilt on each reload so its checks run against the new generation's layers.  A single supervisor owns it and holds its lock for the whole teardown and rebuild, so concurrent reloads can't stop the same instance twice or race for the port.  Once shutdown begins draining, a rebuild comes up already reporting unready, and once health has stopped a reload no longer brings it back.

A single `Reloader` in `pkg/entry` owns every reload, whatever triggered it.  It holds one lock for the whole of a reload, from building the new generation through the swap, so two reloads can't finish out of order.  Reloads requested before `ListenAndServe` hands over its swap function are queued rather than dropped, and the latest one is applied once the server is ready.

Secret watches request a reload without waiting for it.  Closing a generation waits for its secret pollers to stop, so a poller blocked on the reload lock could deadlock a reload that is closing that same generation.  Requests that arrive while one is already queued collapse into it, since the queued reload re-resolves every secret anyway.
